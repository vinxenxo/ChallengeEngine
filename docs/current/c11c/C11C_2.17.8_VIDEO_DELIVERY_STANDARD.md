# C11-C 2.17.8 — Video Delivery Standard and Challenge Capture Contract

## 1. Current decision

The product-level default video delivery profile is **MASTER_1080 = 1080×1920, 9:16**.

The C11-C historical review profile remains **REVIEW_720 = 720×1280**. It is review/evidence output, not the canonical master. **MIN_540 = 540×960** remains the minimum output profile.

This changes delivery policy only. It does not replace the frozen logical social frame or the runtime simulation viewport.

## 2. Geometry layers

Historical Challenges retain their established 1080×1920 simulation coordinate contract and 540×960 logical presentation/source-capture path. Physical delivery is applied after capture.

```text
runtime/presentation
      ↓
Godot Movie Maker — 540×960 source
      ↓
FFmpeg Lanczos delivery transform
      ├── MIN_540   540×960
      ├── REVIEW_720 720×1280
      └── MASTER_1080 1080×1920
```

The resolution of a delivered file is therefore not a gameplay or mechanics parameter.

## 3. Why Challenges do not use the C11-C 720×1280 viewport override

C11-C Visual Loops/Drills have an explicit 540×960 logical social composition and a certified 720×1280 review path. Historical Challenges have a different established capture contract. Applying the C11-C 720×1280 viewport override to Challenges would mix runtime/presentation geometry with delivery policy.

The rule is: **runtime geometry is fixed; delivery geometry is profile-driven and post-capture.**

## 4. Profiles

| Profile | Output | Role |
|---|---:|---|
| `MASTER_1080` | 1080×1920 | default product master |
| `REVIEW_720` | 720×1280 | historical C11-C review/evidence |
| `MIN_540` | 540×960 | minimum social output |
| `META_REELS_FINAL_V1` | 1080×1920 | compatibility alias |
| `LONGFORM_1080` | 1080×1920 | longform |

Profile metadata lives centrally in `profiles/delivery/c11c_video_delivery_profiles.json`.

## 5. Technical delivery contract

The current validated encoder path uses MP4/H.264, YUV 4:2:0-compatible output, progressive scan, constant FPS, closed 3-second GOP, AAC-LC 48 kHz stereo and 192 kbps audio.

The declared product envelope permits 24–60 FPS and ordinary social duration 3–90 s. H.265/VP9/AV1 remain future separately validated encoders rather than implicit substitutions.

## 6. Challenge timing contract

Frames are derived only from the four declarative phases:

```text
round(hook_duration × fps)
+ round(game_duration × fps)
+ round(reveal_duration × fps)
+ round(cta_duration × fps)
```

Legacy `total_duration` is ignored when inconsistent. This preserves the historical 12 s / 720-frame evidence for CHALLENGE_008 and CHALLENGE_009.

## 7. Windows launch contract

The producer uses `System.Diagnostics.ProcessStartInfo`. `--config=<absolute path>` and `--audio-output=<absolute path>` are each constructed as one native argument. The exact command line is retained as `godot_command.txt`.

The previous failure demonstrated why this matters: `--config=` plus a separate path caused `GeneradorMaestro` to emit `CHALLENGE_INVALID`.

## 8. Source validation contract

The source AVI is authoritative. FFprobe must confirm:

- 540×960;
- Challenge FPS;
- canonical phase-sum frame count.

Godot log text is not authoritative for dimensions. On Windows, process-output decoding can turn UTF-8 `×` into mojibake. 2.17.8 forces UTF-8 decoding and retains a non-fatal textual telemetry warning, while FFprobe decides pass/fail.

## 9. Audio adapter boundary

C7 ownership remains unchanged. The producer only adapts the raw PCM input for FFmpeg as `s16le / 44.1 kHz / mono`, then encodes delivery as AAC-LC / 48 kHz / stereo / 192 kbps.

## 10. Frozen boundaries

No change to Challenge mechanics, structural RNG, `SimulationResult`, `winning_frame`, `close_calls`, `WinningFrameDetector`, `RenderedFrameStream`, C11-B 540×960 geometry, C7 contracts or C9 challenge-authoring semantics. Gameplay-semantic changes require a separate checkpoint and regression evidence.
