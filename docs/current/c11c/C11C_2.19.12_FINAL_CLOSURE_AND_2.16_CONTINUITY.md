# C11-C 2.19.12 — Final Closure and 2.16.9 Continuity Record

## Purpose

This document is the closure record for the complete 2.19.x repair line before the final workstation acceptance. It records what was actually reconciled from the 2.16.9 frozen behavioral baseline and what was intentionally left for C11-D.

## 1. Baseline relationship

The immutable behavioral oracle is `ChallengeEngine-C11-C2.16.9 FROZEN.zip`. The 2.19.14 working baseline was compared directly at the `core/` tree. Exactly one file differed:

`core/presentation/rendering/VisualContentPlayer.gd`

The only change was a `qa_mode` exemption around the visual-duration lower/upper bound checks so deliberate QA-duration physical smoke could execute without altering normal production timing policy. No other `core/` file differed.

Conclusion: the large 2.19 repair history did not require a broad engine rewrite. The remaining work was concentrated in tooling, test harnesses, presentation validation, production orchestration, packaging and documentation.

## 2. Closure repairs carried forward

### Encoding and PowerShell

- one BOM where required; no accidental double BOM;
- ASCII-safe executable PowerShell punctuation;
- safe `${Label}` / `${i}` interpolation when a colon follows a variable name;
- explicit optional-property checks under `Set-StrictMode`;
- no `Out-Null` before an object that later consumers need;
- functions returning structured objects suppress incidental diagnostic pipeline output;
- repository root resolved from `$PSScriptRoot`; launchers establish root before relative operations.

### Suite / Producer ownership

- `c11c-suite/` is the sole active Suite surface;
- `c11c-studio/` is retired and non-operational;
- operational test/QA capabilities retain direct console routes plus Suite routes;
- Producer remains orchestration-only and does not duplicate backend truth.

### Worker isolation

- `Workers=7` is real concurrency;
- every worker receives a private temporary Godot project root;
- `.godot`, `override.cfg` and global script-class cache state are worker-local;
- each worker bootstraps the Godot editor class scan before capture;
- canonical field is `WorkerRoot`; `Root` remains only as compatibility alias;
- no global mutex and no serial fallback.

### Challenge-family QA normalization

The historical nine Challenges remain authoritative. QA was corrected to respect actual declarations rather than impose generic assumptions:

- Challenge discovery uses explicit ID matching;
- challenge FPS comes from the declared definition (the current corpus uses 60 FPS);
- Challenges in this branch are validated as video-only where that is the declared contract;
- missing `reveal_duration` is treated as optional/zero by QA; JSON definitions were not mutated merely to satisfy QA.

### Complete-review manifest normalization

Two concrete validator/schema mismatches were repaired without changing generated media:

1. Canonical Visual Loop manifests do not require `output_mp4`; the validator now resolves `output_mp4`, `mp4`, or the deterministic sibling `.mp4`.
2. Canonical technical IDs retain historical names: `kaleidoscope`, `particle_flow`, `vector_field`. The review's editorial/runtime keys are `sacred_symmetry`, `living_particles`, `invisible_forces`. An explicit crosswalk now validates those aliases instead of treating them as identity mismatches.

### FFprobe / process handling

The review and smoke tools retain `ffprobe` objects for later stream inspection instead of piping needed objects to `Out-Null`. This prevents false property-missing failures in strict validation.

The logical corpus runner now distinguishes process-level transient faults from deterministic contract faults. Exact Windows `0xC06D007F` is retryable up to three times. A suite FAIL marker, fatal pattern, timeout, missing PASS marker after exit 0, or another non-zero exit remains a hard failure. V14 also corrected the three stale C10 marker registry entries from `PASS - ...` to the canonical emitted `PASS — ...` form. The current test tree contains 139 registered logical suites.

## 4. What is deliberately deferred to C11-D

Do not normalize every historical identifier or redesign every pipeline while closing C11-C. In D, the Challenge family can be reviewed end-to-end and normalized coherently across:

- Challenge IDs and schemas;
- asset-family/template contracts;
- visual/editorial parity with C11-C;
- audio profiles;
- delivery profiles;
- provenance/manifests;
- seed registry and reuse policy;
- per-video production requests;
- catalog and Suite surfaces.

That is a single D work package, not a reason to reopen the frozen C11-C manufacturing baseline.
