# D5.1 — Canonical Artifact Manifest Contract

## Status and authority

D5.1 converts the D5.0 discovery audit into a curated, declarative manifest for production and provenance relevant D3, D4, and D5 artifacts. The manifest has `status: ACTIVE`, `runtime_authority: NONE`, and `production_execution: false`. It records identity and evidence; it does not authorize production, publish media, move files, rename files, or delete files.

The manifest is intentionally not a raw repository index. It excludes generated caches, `.godot` state, temporary render files, worker scratch, and the general repository file inventory. Governed inputs are selected from the D5.0 audit and checkpoint receipts; each selected source is cross checked against D5.0's path, classification, and content hash evidence.

## Identity and content integrity

`artifact_id` is SHA-256 over canonical UTF-8 JSON with sorted keys and compact separators for exactly these identity fields:

```json
{
  "artifact_type": "...",
  "artifact_role": "...",
  "artifact_version": "...",
  "producer_component": "...",
  "parent_artifact_ids": []
}
```

`relative_path` records physical location and is excluded from the identity input. Moving an artifact therefore does not change `artifact_id`. `content_sha256` separately hashes the exact file bytes and changes if the content changes. Modification time, absolute path, machine name, username, and temporary directories are excluded from identity.

The manifest registers itself and its evidence/receipt by deterministic logical identity. Their `content_sha256` entries are null with `content_hash_state: GENERATED_AFTER_WRITE` to avoid a self-reference cycle. The D5.1 evidence and receipt record the completed manifest byte hash after it is written; the receipt also records the evidence byte hash. The receipt's own hash is reported by the runner and is not embedded into itself.

## Scope and taxonomy

The governed set covers D3 music engine/style declarations, contracts, receipts, provenance evidence, the primary raw deterministic render, and the separate delivery master; D4 request schema, personalization registry, activation policy, contracts, request/plan/authorization records, adapters, acceptance evidence, and receipts; and D5.0/D5.1 audit, contracts, schema, manifest, evidence, and receipt. If two physical paths have the same identity and the same content hash, they are one logical manifest entry with sorted `alternate_relative_paths`.

Artifact types are exactly `REQUEST`, `PLAN`, `AUTHORIZATION`, `MEDIA`, `MANIFEST`, `PROVENANCE`, `VALIDATION_RECEIPT`, `EVIDENCE`, `REPORT`, `SNAPSHOT`, `LOG`, and `TEMPORARY`. Lifecycle states are exactly `ACTIVE`, `HISTORICAL`, `TEMPORARY`, `QUARANTINED`, and `ORPHANED`. This checkpoint does not add `PUBLISHED`, `UPLOADED`, or `DISTRIBUTED`.

Historical route counts from D5.0 remain summary evidence. `docs/history/` entries are never promoted into the active governed set and are explicitly represented by a `HISTORICAL` route summary, without expanding the raw history corpus. The manifest's unmanaged inventory retains the D5.0 orphan candidate count as `ORPHANED`, `governed: false`, `cleanup_authority: NONE`, and `cleanup_performed: false`. D5.1 may resolve a selected candidate only when a retained receipt proves its parent edge; the primary D3.2 raw WAV and D3.3 delivery master are reclassified `ACTIVE` because the D3.3 receipt explicitly names both sides of that delivery edge. Other selected records whose D5.0 lifecycle remains `ORPHANED` are listed for inspection with `governed: false` and `canonical: false`. `ORPHANED` does not mean delete or active.

## Provenance and lineage

Known provenance values come from structured requests, plans, authorization evidence, receipts, and D3 render provenance. Missing values are `UNKNOWN`; not applicable values are null. Filenames and folder names never supply provenance values. Producer identity names the creating component when evidence declares it; otherwise it remains `UNKNOWN`.

D3.3 explicitly names the D3.2 raw source and delivery master, which are registered as distinct media artifacts with a parent link. D4 request-to-plan links are recorded when retained payloads share the declared request ID. Plan-to-authorization lineage references the D4.9 acceptance evidence for the D4.8 hash links. Authorization-to-production-media remains unresolved because no production media was created and renderer policy remains disabled.

## Determinism and validation

Manifest records are sorted by `artifact_id`; all set-like parent and evidence arrays are sorted. Repeated builds must produce equal manifest bytes, equal counts, and no duplicate handover state. The schema is `definitions/c11d/artifacts/C11D_ARTIFACT_MANIFEST_SCHEMA_V1.json`.

The builder validates path-independent identity, content hash behavior, D3/D4 provenance coverage, lineage references, lifecycle vocabulary, frozen C11-C archive identity, retained orphan count, output determinism, and idempotency. It does not migrate, clean, quarantine, or execute production artifacts.
