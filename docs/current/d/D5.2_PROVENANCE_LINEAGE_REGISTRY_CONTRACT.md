# D5.2 — Provenance Lineage Registry Contract

## Authority and input

D5.2 consumes the D5.1 canonical artifact manifest as the sole node source. D3/D4 receipts, evidence, D5.0 audit, and D5.1 evidence are consulted only to prove edges or decisions. The builder does not rescan the repository to discover nodes.

One logical `artifact_id` creates one graph node, even when the manifest records multiple physical locations. Locations remain attached to the node as sorted metadata; copies do not create additional nodes. The registry stores only node index fields and lineage edges, not a second copy of the manifest.

## Edge semantics

Edges use `SOURCE --RELATION--> TARGET`: the source artifact describes its relation to a preceding or supporting artifact. The relation vocabulary is exactly `DERIVED_FROM`, `GENERATED_FROM`, `AUTHORIZED_BY`, `VALIDATED_BY`, `DOCUMENTED_BY`, and `SNAPSHOT_OF`.

An accepted edge requires source and target IDs present in the D5.1 manifest and an evidence artifact also present in that manifest. `edge_id` is SHA-256 over canonical source ID, relation, target ID, and evidence artifact ID. Evidence records its type, checkpoint, relative path, and claim. Filename-only, directory-only, or guess-only relations are rejected. No `COPIED_FROM` relation is used for duplicate physical copies.

The D3.3 receipt explicitly names both the D3.2 raw render and D3.3 delivery master, supporting `delivery master --DERIVED_FROM--> raw render` and `delivery master --VALIDATED_BY--> D3.3 receipt`. The D3.2 raw content hash is compared with D3.2 render provenance before accepting its validation edge.

D4 plan-to-request edges use matching request IDs retained in the manifest. D4.8 authorization evidence is a decision artifact with `decision: BLOCKED`, renderer policy `DISABLED`, and reason `RENDERER_POLICY_DISABLED`. It is linked as decision evidence derived from the plan where D4.9's hash integrity evidence proves the relation. No positive `AUTHORIZED_BY` edge is created. D4.9 acceptance evidence validates the plan through its recorded hash checks.

## Nodes, roots, and orphans

Each node contains its manifest identity, type, role, lifecycle, canonical/governed flags, physical locations, parent IDs, and decision context only where applicable. The nine D5.1 `ORPHANED` records remain nodes with `lineage_status: ORPHANED`, no cleanup authority, and no automatic cleanup. They are not lineage roots. A root has valid identity/provenance but no incoming source parent relationship; roots and orphans are separate classifications.

The 12,304 global unmanaged candidates remain an external count copied from D5.0. They are not expanded into graph nodes and are not reclassified or cleaned. D5.1 resolves the two selected D3 media records using its receipt-backed raw/master relation; the original D5.0 count remains recorded unchanged.

## Validation

The builder checks every accepted edge endpoint and evidence ID against D5.1, removes invalid edges from the accepted graph, validates a DAG, rejects a synthetic missing-parent edge, and detects an in-memory synthetic cycle. It creates deterministic `parents_by_artifact` and `children_by_artifact` indexes. Node, edge, unresolved edge, root, and orphan ordering is stable.

Idempotent runs must produce identical registry, evidence, and receipt hashes. D5.1's 75 logical nodes, 79 locations, 66 governed/active nodes, and 9 orphans are checked against the consumed manifest. The frozen C11-C archive hash is reverified. No file is moved or deleted; runtime authority remains `NONE` and production execution remains false.
