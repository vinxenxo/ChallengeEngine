# C11-D D6.4 — Request / Plan / Provenance Integration

**Status:** integration adapter checkpoint; runtime authority remains `NONE`.

## Purpose

D6.4 connects the already-closed D4 canonical request/plan path with the D6 seed governance layer and the existing D5 provenance/lineage model. It produces reference-only integration evidence. It does not replace or modify any authoritative D4, D5, D6.1 or D6.2 implementation.

The canonical flow is:

`D4.2 canonical request -> D6.2 seed resolution -> D4.4 canonical plan -> D6.4 integration/provenance evidence`

The D4.4 production plan remains owned by `canonical_production_orchestrator`. D6.4 owns only its integration evidence.

## Ownership

- Request SHA-256: `c11d_production_request_normalizer`.
- Seed-resolution identity: `c11d_seed_resolver`.
- Seed registry identity: `c11d_seed_registry`.
- Governance policy identity: `c11d_seed_governance_policy`.
- Plan SHA-256: `canonical_production_orchestrator`.
- D6.4 integration evidence: `seed_request_plan_integrator`.

No D6.4 artifact may claim ownership of the D4 request, D4 plan, D6.1 registry/policy or D6.2 resolver.

## Canonical seed provenance

The only active canonical mappings are:

- `request.seed -> gameplay.seed -> GAMEPLAY`.
- `request.music_seed -> music.seed -> MUSIC`.

Explicit seed values pass through unchanged. Equal numeric values are valid when the authorities and domains remain independent. `request.seed=777` and `request.music_seed=777` are two valid independent resolutions, not an identity collision.

Changing the gameplay seed must not change MUSIC resolution. Changing the music seed must not change GAMEPLAY resolution.

## Personalization and variation

D6.4 does not make personalization or `variation_index` seed sources. Existing valid personalization changes and variation changes must preserve the resolved gameplay/music seeds unless a separately governed future contract explicitly changes this policy.

## Derivation and master seed

D6.2 derivation capability is available but runtime activation remains disabled by the D6.1 policy. D6.4 therefore uses explicit `request.seed` and `request.music_seed` only.

`master_seed = NOT_ADOPTED`. D6.4 does not introduce a master seed or treat one as a canonical authority or active derivation parent.

## D5 provenance compatibility

D6.4 emits provenance compatible with the D5 lineage model but does not mutate the D5.2 lineage registry. D4.8 blocked governance remains a decision record, not an `AUTHORIZED_BY` grant. No physical authorization is inferred or materialized.

## Integrity controls

D6.4 validates request hash, plan hash, seed-resolution identity, registry identity, policy identity, seed values, authority/domain mappings, D3 music isolation, D4 seed separation and D4.8 blocked status.

Negative controls reject tampering, cross-domain mappings, missing seeds, unauthorized derivation, `master_seed`, personalization/variation as seed sources, shared RNG/Producer auto-selection as canonical sources and protected C11-C surfaces such as `winning_frame` and `close_calls`.

## Runtime and mutation boundary

D6.4 never activates production. Runtime authority is `NONE`; production, renderer, Godot production and FFmpeg production execution remain false.

The validator runner may change only `artifacts/tests/c11d_d6/d6_4/`. D4, D5, D6.1, D6.2, D6.3, Producer, renderer, gameplay, simulation and frozen C11-C inputs are read-only.

The four generated JSON evidences are deterministic UTF-8 without BOM and contain no dynamic timestamps or random test data. Two executions must produce identical bytes and SHA-256 values.
