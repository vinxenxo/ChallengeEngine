# C11-D D5.5 — Full D5 Acceptance Contract

## Purpose

D5.5 is an acceptance-only checkpoint. It consumes the published D5.0 audit, D5.1 canonical artifact manifest, D5.2 lineage registry, D5.3 topology validation, and D5.4 lifecycle governance evidence. It validates agreement across those sources and does not repair, regenerate, or rewrite predecessor evidence.

## Inputs of record

- D5.0 audit, validation receipt, and D3/D4 receipt inventory.
- D5.1 manifest, manifest evidence, and validation receipt.
- D5.2 lineage registry, lineage evidence, and validation receipt.
- D5.3 topology validation, consistency matrix, and validation receipt.
- D5.4 lifecycle validation, quarantine matrix, policy, and receipt.
- Existing D3/D4 receipts and evidence referenced by the manifest and lineage graph.
- The frozen C11-C ZIP and the source-tree/build hashes recorded below.

The harness reads actual serialized fields and validates their values; a missing or inconsistent required field blocks acceptance with a checkpoint-specific diagnostic.

The D5.0 receipt inventory contains 19 receipts across D1-D4. Of those, 14 receipt paths belong to D3/D4. D5.5 validates both the total inventory count and the D3/D4 subset against the actual D5.0 audit instead of relabeling D1/D2 receipts as D3/D4.

D3 raw media and delivery master remain distinct; the master’s `DERIVED_FROM` and validation evidence are checked. D4 request/plan/governance/acceptance edges are checked, and D4.8 blocked governance must not be represented as an authorization grant.

## D5.1 receipt self-hash exception

The D5.1 validation receipt does not declare its own content hash. This is recorded as `DECLARATION ABSENT / NON-BLOCKING SCHEMA DECLARATION`. D5.5 still verifies the manifest and evidence hashes declared by the D5.1 receipt. The absent self-hash is not an evidence hash failure.

- ZIP SHA-256: `D85425CF18C5211C8497574F4FC66202D613EACC0EC14CD4E2FEF0B24F634A32`
- TREE SHA-256: `2D39B7B923B42CDC6647A4D25493B75023CDD19CEE18214BBDE1FDD295B8F256`
- `build_factory.py` SHA-256: `3DB8FBC21CF0C78430018424F83A9EED5B42DF34A3908BA152F6771F0679D2A3`

The frozen objects are read-only inputs. D5.5 does not rebuild or modify them.

## Mutation and runtime fences

The PowerShell runner snapshots the repository worktree before and after the acceptance harness. Git's internal `.git` metadata is excluded; among worktree files, the only excluded paths are the three D5.5 evidence outputs. Any other addition, deletion, move, or content change fails with `FILESYSTEM_MUTATION_FAILURE`. Temporary fixture files are not created by D5.5.

D5.5 performs no lifecycle transitions, quarantine actions, cleanup, movement, deletion, or production work. Runtime authority is `NONE`; production, renderer, Godot, and FFmpeg production execution are false.

## Determinism and outputs

The harness builds the acceptance evidence twice in memory and requires equal canonical JSON. Its UTF-8 JSON has stable key ordering and no timestamps. The three outputs are:

- `artifacts/tests/c11d_d5/d5_5/d5_5_acceptance_matrix.json`
- `artifacts/tests/c11d_d5/d5_5/d5_5_acceptance_summary.json`
- `artifacts/tests/c11d_d5/d5_5/d5_5_acceptance_receipt.json`

The operator runs the PowerShell runner twice and compares all three output SHA-256 values to establish end-to-end idempotence.

## Acceptance gate

D5.5 is `PASS / CLOSED` only when D5.0–D5.4 are PASS/CLOSED, the cross-check invariants agree, D3/D4 preservation passes, all required negative tests pass, frozen C11-C identity matches, deterministic output passes, and the mutation guard reports no changes outside D5.5 evidence. Any discrepancy blocks D5.5; its responsible predecessor must be repaired in its own checkpoint before acceptance is rerun.

On closure, the next checkpoint is **D6 — Seed Registry and Governance**. D5.5 does not implement D6.
