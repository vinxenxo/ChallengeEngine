# C11-E Architecture Decision Record and Backlog V1

**Date:** 2026-11-03
**Input baseline:** E0/E1/E2 accepted records, C11-C 2.19.12 contracts, C11-D D3/D9 contracts, E3.2 commit `3cc1caa6d740b1525a4ebb30a4ff7f02868ac5a8`.

This document records durable engineering decisions and rationale for future implementation and context handover. It records project reasoning and evidence, not private model deliberation.

## A. Decisions

### ADR-E-01 — Complete three-family product, not a CH001 demo

**Decision:** The product is Challenge + Visual Loop + Visual Drill, on-demand final MP4, with C mechanics preserved, D presentation/editorial, family-correct music, mux, QA and provenance.

**Rationale:** E2 CH001 proves only a single title slot. The V13 roadmap and E product-scope contract explicitly define the complete family target. E2 is an integration seam, not the product boundary.

### ADR-E-02 — GUI is the primary operator workflow; CLI remains compatible

**Decision:** From this implementation onward the operator works through the existing Producer GUI. CLI remains a thin adapter used by automated tests and separate-process parity.

**Rationale:** Avoid duplicated workflows and user effort. Both surfaces must call one canonical service; the GUI cannot own business logic.

**Constraint:** Do not add a sixth suite module or a new Producer application. The existing five `c11c-suite` modules remain authoritative.

### ADR-E-03 — One E production service, family-specific adapters

**Decision:** One canonical E service normalizes requests, binds editorial/music contracts, chooses the family adapter, dispatches C-compatible runners, collects results and produces receipts. Challenge/Loop/Drill adapters remain distinct.

**Rationale:** Family consumers and timing semantics differ. A common service should unify orchestration and provenance, not flatten all visual binders into one implementation.

### ADR-E-04 — C11-C source and gameplay truth remain immutable

**Decision:** Do not change the frozen manifest, `core/audio`, protected C11-C generators, `SimulationResult`, `winning_frame`, `close_calls`, RNG ownership, frame stream, mechanics or source definitions. E adds adapters/sidecars and orchestration at the boundary.

**Rationale:** C11-C 2.19.12 is the working production baseline and must remain reproducible while E is qualified.

### ADR-E-05 — Music uses an orchestration strategy by family, not one forced sound

**Decision:** Challenge uses D3 Music Engine V5 and `challenge_8bit_v1`. Loop/Drill retain their existing C11-C family-aware generator and declarative profiles. The E adapter calls their existing audio-only entry point with `request.music_seed` separately from the visual render's `request.seed`; no generator fork or source modification.

**Rationale:** D3.0/D3.1 specify a shared engine/profile architecture but explicitly protect Loop/Drill runtime behavior. C11-C music contracts encode real family/grammar semantics: Loop music uses seed + visual family + grammar; Drill music uses seed + drill family, with a global ambient/END_CTA envelope. Replacing them with Challenge 8-bit would erase validated product identity. A shared E orchestration interface preserves a common seed/provenance contract without forcing one waveform.

**Open compatibility check:** Verify in the active checkout that `C11CSafeAmbient.py` / `generate_c11c_family_music.py` can be called as an isolated audio stage and that `music_seed` can be passed positionally without also changing visual inputs. If this exact seam is not available, stop and design an E-only invocation adapter; do not clone or modify the C generator.

**Recorded ambiguity:** The E product-scope document says “music generated by D3” across all three families, while D3.0/D3.1 and C11-C music contracts preserve Loop/Drill behavior. This ADR resolves implementation sequencing in favor of the non-interference contract. Reconsider only with a versioned profile/equivalence review and explicit decision.

### ADR-E-06 — Duration comes from the verified visual artifact

**Decision:** E3 obtains `duration_seconds`, frame count and frame rate from the exact input MP4 via FFprobe and cross-checks them. The V5 CLI's four-second default is never used as a production default.

**Rationale:** The D3.1 engine interface requires duration. E2 R4 is 270 frames at 30 fps = 9 seconds; older D9.2 footage is 540 frames at 60 fps = 9 seconds. Duration is a property of the chosen output media, not a static global constant.

### ADR-E-07 — BPM 104 is a pilot fixture, not a default

**Decision:** The first CH001 comparison may use 104 BPM and variation 0 because the historical D9.2 runner explicitly supplied those values. Do not expose 104 as an assumed universal default or silently inject it into E1.

**Rationale:** The prose D9.2 contract and V5 declarative profile do not establish a general tempo default. The runner is evidence for one pilot case only.

### ADR-E-08 — Apply D3.3 mastering without extending final video duration

**Decision:** Preserve the raw WAV. Reproduce the active D3.3 loudness/mastering QA, including the 30-second repeated measurement window and `loudnorm=I=-14:TP=-1:LRA=7` implementation precedent. Then create a final audio delivery segment aligned to the verified video duration and test the trimmed result.

**Rationale:** D3.3 separates deterministic source synthesis from delivery mastering. The 30-second sample is a measurement/mastering workflow, not the final length of a shorter MP4. The raw file remains available for provenance and repeatability.

**Unresolved implementation detail:** Confirm the exact trim/segment strategy and its boundary behavior before production acceptance. Do not introduce a fade or other DSP not authorized by source contract; test clicks/discontinuities and report rather than improvise.

### ADR-E-09 — Use D9.2 as Challenge A/V mux precedent, not as a global format guess

**Decision:** For the first Challenge A/V test, refresh and use the historical D9.2 runner's H.264 video stream copy, AAC 192 kb/s, 48 kHz stereo, `-shortest`, `+faststart`, exactly one stream of each type and 0.15-second duration-difference tolerance.

**Rationale:** D9.2 contains an actual successful implementation and FFprobe evidence. The target 48 kHz delivery resamples the 22.05 kHz V5 raw WAV. All values must be re-pinned to active source code. Do not assume every Loop/Drill profile uses the same settings without contract review.

### ADR-E-10 — Presentation/editorial is allowlisted and binder-specific

**Decision:** Common editable fields: title, subtitle, call_to_action, language; Challenge-only player_name and challenge_label. Reserved fields stay disabled. Every field must map to a verified family binder slot and time window.

**Rationale:** D9.8 gives strict scope/inheritance rules. C11-C presentation differs by family. Title is not hook; CTA precedence and phase semantics are protected.

### ADR-E-11 — 99 runnable cases are provisional; retain 101 target

**Decision:** Preserve Matrix101 = 54 Challenge + 27 Loop + 20 Drill. With CH_008 and CH_009 held, provisional runnable = 52 + 27 + 20 = 99.

**Rationale:** The V13 parenthetical `54+27+18` is inconsistent with the stated inventory and held IDs. This is a documentation correction only. Confirm all IDs from the active producer schema before E7; do not alter CH_008/009 timing definitions without authority.

### ADR-E-12 — E gates do not promote production authority

**Decision:** Physical E renders are isolated tests under `artifacts/tests/c11e`; release authority remains NONE until E8.

**Rationale:** E2/E3/Smoke/matrix evidence validates a new branch of production but does not replace C11-C until independent acceptance and explicit promotion.

## C. Test pyramid

1. Contract/static: schema, resolver, binder maps, GUI form contracts, protected-file pins.
2. Unit: deterministic audio render, seed separation, profile identity, editorial resolver, duration calculation, FFmpeg argument model.
3. Integration: same E service called by GUI and CLI; audio engine invocation; mastering pipeline; mux/probe.
4. Physical family pilot: real MP4 with editorial/layout/music; one isolated run at a time.
5. Smoke18 and Matrix101 after family integration.
6. Human review: visual frame/contact-sheet review and listening/mobile playback review recorded separately from machine PASS.

## D. Always-on acceptance invariants

- `request.seed` never becomes `request.music_seed`; no automatic seed generation.
- Music-seed-only changes cannot alter video frame output.
- Gameplay-seed-only changes cannot alter generated audio when family/profile/grammar/music seed are fixed.
- Editorial-only changes do not alter mechanic truth or seed domains.
- Audio disabled means no audio generation or mux and a precise disabled state in the receipt.
- Every artifact has source commit, profile/spec hashes, request hash, seeds, FFmpeg/FFprobe versions, output hashes and QA status.
- No final status is PASS without exit code 0, structured receipt and all required media evidence.
