## Root cause

The static D9.15 preflight intentionally checks structural GUI readiness and must not infer operator evidence. Separately, the candidate evaluator compared the static definition contract's status instead of validating the generated sealed acceptance checkpoint. D9.16 hardcoded operator evidence as REQUIRED and always carried the D9.15 evidence blocker forward. The canonical recorder had already been correctly finalized; the consumer paths had not been connected to it.

## Correction

- Candidate evaluator calls the canonical recorder's `validate_acceptance_checkpoint()` and verifies the current append-only ledger, each evidence file hash/size, requirements seal, checkpoint seal and frozen C11-C manifest binding.
- A valid canonical checkpoint takes precedence over the historical candidate-only waiver. A present invalid/stale checkpoint fails closed; it cannot silently fall back to the waiver.
- D9.16 calls the same validator, reports operator evidence PASS/CLOSED only when verified, adds checkpoint/ledger hashes to the receipt, and removes the D9.15 blocker only when the checkpoint is valid. D9.14 remains BLOCKED and full D9.16 stays BLOCKED_AS_REQUIRED.
- Aggregate Suite accepts either a validated canonical closure or the historical candidate-only waiver, because both states can legitimately exist in different trees; it asserts the status from the current candidate report rather than one stale hardcoded value.
- Candidate regression synthesizes the 13-pairing ledger and checkpoint in an isolated temporary tree, then confirms tampered checkpoint fields and modified evidence bytes are rejected.
