# C6-F0.3 — Multi-Content, Temporal & Runtime Foundation

## Authority and scope

This document is the canonical cumulative architecture/status record for the **C6-F0.3 foundation branch**.

It covers the closed/certified foundations C6-F0.3.1 through C6-F0.3.4 and the implemented but not yet runtime-certified C6-F0.3.5 boundary.

Older checkpoint handovers remain historical evidence. This document does not rewrite their frozen mathematical contracts; it consolidates the resulting architectural state.

---

## 1. Executive Summary

C6-F0.3 establishes three independent capabilities without contaminating the sovereign Challenge domain:

1. **Multi-content authoring boundaries** for `visual_loop` and `visual_drill`.
2. **Reusable temporal primitives** extracted from legacy Challenge timing.
3. **A polymorphic content runtime boundary** routed by exact `(kind, subtype)` matching.

The governing architectural law is:

```text
Domain-specific authoring
        ↓
Content-specific runtime selection
        ↓
Content-specific runtime
        ↓
Rendered Frame Stream
        ↓
Presentation / Rendering
        ↓
Export
        ↓
Provenance / Manifest
```

Challenge remains sovereign. Visual content is not modeled as a Challenge mechanic, simulation, score system, or winning-frame problem.

## 3. C6-F0.3.2 / F0.3.3 — Schema Boundary and Shared Envelope

### ContentEnvelope

The shared envelope is governed by:

```text
res://core/authoring/schemas/content_envelope_schema.json
```

It carries metadata only:

```text
schema_version
content_id
content_version
kind
subtype
engine_version
authoring_version
presentation
assets
audio
provenance
```

The envelope is intentionally **visual-only**:

```text
kind = visual_loop | visual_drill
```

`challenge` is not accepted by the multipurpose envelope.

### Challenge sovereignty

Challenge retains:

- its own schemas;
- its own orchestration;
- its own simulation contract;
- its own RNG semantics;
- its own winning-frame semantics;
- its own presentation timeline compatibility.

The C6-F0.3 envelope is therefore not a universal document model.

### ContentSchemaValidator

`ContentSchemaValidator.gd` is fail-closed at document level and nested object boundaries. The current contract includes:

- `additionalProperties: false` behavior;
- uppercase `content_id` pattern `^[A-Z0-9_]+$`;
- closed enums for visual generator/task/shape/pattern/pacing fields;
- numeric bounds such as `boundary_tolerance` in `[0.0, 0.01]`;
- `transition_window_frames >= 0`;
- cross-field temporal invariant:

```text
frame_count == round(duration * fps)
```

`frame_count` remains a verifiable declaration, not an independent runtime authority.

## 4. C6-F0.3.4 — Temporal Abstraction

### TemporalCore

```text
res://core/authoring/TemporalCore.gd
```

`TemporalCore` owns only:

```text
fps
total_frames
_current_frame
duration_to_frames()
advance()
get_current_frame()
is_finished()
```

The frozen conversion rule is:

```text
maxi(0, int(round(duration_seconds * fps)))
```

`advance()` is monotonic and does not clamp or wrap. `TemporalCore` therefore contains no loop semantics and no Challenge phase semantics.

### ChallengeTimeline

The current source file is:

```text
res://core/authoring/ChallengeTimeLiine.gd
```

and exposes the class name `ChallengeTimeline`.

It remains a sovereign Challenge timeline with observable semantics:

```text
HOOK → GAME → REVEAL → CTA
```

Zero-frame phases are omitted effectively, while `GAME` remains mandatory.

Historical API compatibility remains:

```text
get_current_block()
is_phase_enabled()
get_game_index()
```

### VideoTimeline

```text
res://core/timeline/VideoTimeline.gd
```

remains a compatibility shim extending `ChallengeTimeline`.

It is not removed or generalized into a universal phase engine.

### VisualLoopTimeline

```text
res://core/authoring/VisualLoopTimeline.gd
```

extends `TemporalCore` and owns the only loop wrapping semantics:

```text
loop_frame     = _current_frame % total_frames
loop_iteration = _current_frame / total_frames
```

The absolute temporal cursor remains monotonic.

### VisualDrillTimeline

```text
res://core/authoring/VisualDrillTimeline.gd
```

extends `TemporalCore` and deliberately defines **no phases**.

No speculative `instruction`, `exercise`, `closing`, `reveal`, or similar phase model is introduced by the foundation.

model["cta_main"] = comp.get("cta_main", "LINK IN BIO")

Dedicated regression coverage:

## 6. C6-F0.3.5 — Content Runtime Boundary

### 6.1 Core architectural decision

The foundation does **not** introduce a universal `ContentDefinition` superclass and does **not** place Challenge inside `ContentEnvelope`.

The common layer is instead a **behavioral runtime boundary**:

```text
routing
runtime lifecycle
frame progression
frame cardinality
frame ordering
render-ready frame stream
completion / failure
```

Domain meaning remains inside the domain runtime.

### 6.2 ContentRuntime

```text
res://core/runtime/ContentRuntime.gd
```

The common runtime contract is intentionally small:

```text
initialize(definition)
is_initialized()
get_error()
get_current_frame()
is_finished()
get_frame_count()
get_fps()
get_rendered_frame_stream()
next_frame()
```

It has no dependency on:

```text
SimulationResult
WinningFrameDetector
RNG
ChallengeMechanic
PresentationUI
CTAComponent
Exporter
FFmpeg
```

### 6.3 ContentRuntimeRegistry

```text
res://core/runtime/ContentRuntimeRegistry.gd
```

Routing is exact and fail-closed:

```text
(kind, subtype) → runtime factory
```

There are no wildcard routes and no silent fallback runtime.

The registry rejects, among other cases:

```text
missing routing metadata
empty routing metadata
duplicate registration
invalid factory
factory returning a non-ContentRuntime
unregistered route
runtime initialization failure
```

`subtype` remains open in the frozen visual schema. Therefore visual subtypes are not invented globally by the registry; consumers must register explicit routes.

Challenge routing is internal to the runtime boundary and uses:

```text
(challenge, mechanic_id)
```

without adding `challenge` to `ContentEnvelope`.

### 6.4 ChallengeRuntime

```text
res://core/runtime/ChallengeRuntime.gd
```

`ChallengeRuntime` is a **boundary adapter**, not a reimplementation of Challenge.

Its role is to delegate into the existing sovereign Challenge pipeline, then expose the result externally as the common frame-stream contract.

Internally the Challenge branch may continue to use:

```text
SimulationResult
WinningFrameDetector
RNG
ChallengeMechanic
VideoTimeline
```

The common runtime API does not expose those types.

### 6.5 VisualLoopRuntime

```text
res://core/runtime/VisualLoopRuntime.gd
```

Uses `VisualLoopTimeline` and emits logical render-ready state containing visual-domain concepts such as:

```text
loop_frame
loop_iteration
generator
layers
loop configuration
```

It does not create Challenge phases, scoring, winning frames, or Challenge RNG dependencies.

### 6.6 VisualDrillRuntime

```text
res://core/runtime/VisualDrillRuntime.gd
```

Uses `VisualDrillTimeline` and exposes only schema-defined exercise state plus monotonic frame/progress information.

It does not invent a phase model.

## 7. Rendered Frame Stream

```text
res://core/runtime/RenderedFrameStream.gd
```

`RenderedFrameStream` is the common runtime output boundary.

It means:

> an ordered sequence of logical, render-ready frame states that Presentation/Rendering can consume.

It is **not**:

```text
rasterized pixels
RAW AVI
MP4
FFmpeg bytes
```

Each frame minimally contains:

```text
frame_index
payload
```

The stream enforces:

```text
non-empty kind
non-empty subtype
fps > 0
frame indices contiguous from 0
payload present per frame
```

The payload remains opaque to generic runtime infrastructure.

### Domain payload ownership

Challenge payloads may contain Challenge frame snapshots internally.

Visual Loop payloads may contain loop/generator state.

Visual Drill payloads may contain stimulus/target/trajectory/task state.

The common stream does not reinterpret these payloads as one universal semantic model.

## 8. Presentation / Rendering / Export Boundaries

The approved dependency direction is:

```text
Domain Runtime
      ↓
Rendered Frame Stream
      ↓
Presentation / RenderModel
      ↓
Rendering
      ↓
Export
      ↓
Provenance / Manifest
```

### Presentation

Runtime code does not know UI objects such as:

```text
PresentationUI
CTAComponent
WinningHighlight
```

Presentation-specific adapters convert domain frame state into the existing `RenderModel`/UI representation.

### Rendering

Rendering owns actual scene composition and pixels.

### Export

Export owns the encoding/container boundary, including FFmpeg/FFprobe integration. The runtime never emits an MP4.

### Factory

`build_factory.py` remains production orchestration. It is not promoted into a universal content runtime merely because it already coordinates Godot, FFmpeg and manifests.

The existing factory version remains:

```text
0.10.0
```

and the manifest contract remains `1.0`.
