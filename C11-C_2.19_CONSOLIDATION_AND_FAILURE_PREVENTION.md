# C11-C 2.19 — Consolidation & Failure-Prevention Rulebook

Revision: 2.19.12
Date: 2026-09-29
Status: active engineering guidance; C11-C is not frozen until workstation acceptance is green.

## 1. Purpose

This document consolidates the operational lessons discovered while reconciling the immutable 2.16.9 frozen baseline with the 2.19.x C11-C repair/consolidation line. It exists so future maintenance and the C11-D branch do not repeat avoidable QA, PowerShell, encoding, launcher, orchestration or documentation failures.

## 2. Baseline relationship

`ChallengeEngine-C11-C2.16.9 FROZEN.zip` is the immutable recovery/debug oracle. It is not to be modified.

The 2.17 overlay was cumulative on 2.16.9: it added pre-challenge foundation, Producer/documentation and additive delivery tooling while intentionally preserving the frozen engine mechanics and truth boundaries.

The 2.19.x work therefore has to be interpreted primarily as consolidation of tooling, Suite ownership, QA, orchestration, delivery validation, worker isolation and documentation. Direct shared-core comparison showed only a narrow `VisualContentPlayer` QA-mode duration-check delta between the inspected 2.16.9 and 2.19.14 trees; the observed late failures were predominantly in runners/tests/launchers rather than simulation truth.

## 3. Mandatory repair method

Use this sequence for every failure:

`FAIL -> reproduce -> locate exact file -> compare 2.19.x with 2.16.9 -> minimal change -> targeted test -> regression -> checkpoint`

Do not create a broad overlay when a one-line test/runner correction is sufficient. Every overlay must list exact modified paths and must exclude unrelated engine files.

## 4. Windows PowerShell 5.1 rules

### 4.1 Variable references followed by `:`

Under Windows PowerShell 5.1, strings such as `$Label:` or `$i:` can be parsed as scoped-variable syntax and fail with `InvalidVariableReferenceWithDrive`.

Use:

```powershell
throw "${Label}: actual=$Actual expected=$Expected"
throw "Worker sandbox copy failed for slot ${i}: robocopy exit=$robocopyExit"
```

Do not rely on `$Label:` or `$i:` inside double-quoted strings.

### 4.2 Em dash and non-ASCII console text

A PowerShell `.ps1` must not depend on a UTF-8-without-BOM interpretation. A non-ASCII console character such as an em dash can trigger parser/encoding problems when the active file is read using the Windows PowerShell 5.1 default code page.

For active operational `.ps1` files:
- encode as UTF-8 with exactly one BOM (`EF BB BF`);
- prefer ASCII punctuation in executable/error messages when Unicode is not important;
- never introduce an em dash merely for cosmetic output in a PowerShell runner.

### 4.3 BOM discipline

One BOM is valid for the active `.ps1` files. A double BOM (`EF BB BF EF BB BF`) is invalid and can make PowerShell fail at character 1.

Never prepend a BOM to bytes that already contain one. When generating files programmatically, decode with UTF-8-SIG, then write exactly one BOM.

### 4.4 PowerShell Parser audit

A parser audit must pass the target path to the actual `System.Management.Automation.Language.Parser.ParseFile` path parameter. Do not confuse the parser's parameters with arguments intended for `powershell.exe`.

The earlier audit produced 55 false failures because it misrouted the path. After correcting the audit itself, only one real syntax failure remained: the `$i:` worker string. This distinction is important: an audit failure must first be classified as an auditor failure versus a target-script failure.

### 4.5 `$LASTEXITCODE` and StrictMode

With `Set-StrictMode -Version Latest`, do not assume an external-process exit variable has already been established. Capture the process result immediately after the invocation and then inspect it.

Prefer a pattern equivalent to:

```powershell
& powershell.exe ...
$exit = $LASTEXITCODE
if ($exit -ne 0) { throw "... exit code $exit" }
```

Do not read `$LASTEXITCODE` much later after unrelated operations.

## 5. JSON / StrictMode compatibility

Direct access to an absent JSON property throws under StrictMode. Legacy Challenge definitions are not guaranteed to expose every historical phase property.

`CHALLENGE_003` is the current compatibility example: its `video` object declares `fps`, `hook_duration`, `game_duration` and `cta_duration`, but no `reveal_duration`. Its effective timeline is 12 seconds / 720 frames at 60 FPS.

The correct compatibility pattern is property inspection:

```powershell
$revealDuration = 0.0
$revealProperty = $Video.PSObject.Properties['reveal_duration']
if ($null -ne $revealProperty) {
    $revealDuration = [double]$revealProperty.Value
}
```

Do not rewrite the Challenge JSON merely to make QA pass. The canonical runner and current C11-C QA should normalize an absent optional reveal phase to zero.

## 6. ffprobe object lifetime

A helper that returns an ffprobe object must not be piped to `Out-Null` when the caller later needs its properties.

Bad:

```powershell
$probe = Assert-Media ... | Out-Null
$probe.streams
```

Correct:

```powershell
$probe = Assert-Media ...
$probe.streams
```

This was the cause of the post-`CHALLENGE_001`/`CHALLENGE_002` family-coverage failure that reported a missing `streams` property.

## 7. Challenge discovery and timing

Use explicit extension/base-name matching when enumerating the canonical nine definitions:

```powershell
Where-Object {
    $_.Extension -ieq '.json' -and
    $_.BaseName -match '^CHALLENGE_[0-9]{3}$'
}
```

Do not use a PowerShell wildcard pattern as the only proof that the canonical nine definitions were discovered.

Challenge FPS is definition-driven. The active nine definitions use their declared `video.fps`; the global visual-review 30 FPS rule must not be applied to Challenge capture.

The Challenge review matrix is video-only in C11-C. Do not add audio to a Challenge just because a generic family validator expects audio for Loop/Drill/Longform products.

`MIN_540` is a diagnostic delivery profile that avoids the post-capture upscale. It does **not** shorten or alter the Challenge timeline and does not replace `REVIEW_720` acceptance evidence.

## 9. Launcher and path rules

Scripts below `tools/qa/c11` resolve repository root from `$PSScriptRoot` with three parent traversals.

Scripts below `c11c-suite/c11c-test` resolve repository root with two parent traversals.

Suite BAT launchers must establish `C11C_PROJECT_ROOT` and normalize with `cd /d` before launching PowerShell/Python/Godot.

Do not use a working-directory assumption based on the caller's current directory.

## 10. Suite ownership and script registration

`c11c-suite/` is the active operational Suite. `c11c-studio/` is retired.

Every new console runner/test must have a Suite entry. For an operational QA tool, registration is required in the appropriate Test surface and, when applicable, in Producer and Maintenance. The Challenge family fast diagnostic is registered in all three surfaces and covered by Suite self-test / Producer GUI contracts.

Do not create a new standalone console tool that can only be reached by a raw filesystem path.

## 11. Worker and override.cfg rules

The historical source of capture-state chaos was shared mutable state. Workers must use private temporary Godot roots exposed through `WorkerRoot`.

Forbidden:
- shared worker `override.cfg`;
- global mutex as a workaround;
- serial fallback that hides concurrency problems.

Final physical acceptance must demonstrate observed concurrency greater than 1 with `Workers=7` and must verify the repository root `override.cfg` is not contaminated.

The Challenge producer may temporarily quarantine the root `override.cfg` while capturing natively, but it must restore the exact prior state and leave no `.override.challenge_quarantine_*.cfg` leak.

## 12. Producer review routing

The GUI operation `REVIEW_CHALLENGES` must invoke the current C11-C bulk QA:

`tools/qa/c11/run_c11c_challenge_bulk_qa.ps1`

It must never silently route to the historical `run_c11a1_challenge_bulk_qa.ps1`.

The historical C11-A.1 QA remains available as historical compatibility tooling and must not be relabelled as the current C11-C review.

## 13. Documentation hygiene

Current operational documents must be unversioned consolidated authorities. Historical 2.19.x receipts and repair notes remain evidence, not current instructions.

Every closure checkpoint should update:
- consolidated current state;
- documentation index;
- command sheet;
- release history;
- current changelog;
- master handover;
- start prompt;
- any Suite/Producer manifest that names an active launcher.

Avoid copying old version-specific instructions forward without checking the current filesystem and launcher ownership.

## 14. Closure gate for C11-C 2.19.12

Do not mark the branch frozen until fresh workstation evidence is green for:

1. Suite self-test.
2. Producer self-test and GUI contract.
3. PowerShell 5.1 parse audit.
4. Focused contracts and one-video smoke.
5. Challenge family fast diagnosis, then family coverage through all nine Challenges.

## 15. C11-D entry principles

After the C11-C freeze, treat 2.19.12 as immutable baseline. Evolve D through additive checkpoints.

The first major D work package is the Challenge family: bring the established C11-C visual/editorial guide to Challenges without reopening frozen engine truth. That includes composition, typography and musical treatment, while keeping Challenge timing and mechanics isolated.

The next asset layer should support interchangeable retro-game-style asset families as declarative templates that can be bound to different Challenge mechanics without duplicating mechanics.

The music work should extend procedural environmental composition while keeping audio deterministic and semantically decoupled from gameplay state.

Video personalization should be declarative: palette, asset family, typography, copy variants and delivery profile should be inputs to production orchestration, not hidden changes to engine truth.
